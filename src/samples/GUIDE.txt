SWARM GUIDE

swarm runs chains: ordered steps, each a tool (a shell command), an agent
(Claude Code, Codex or another CLI given a prompt, returning named fields),
a user step (waits for a person's decision), a sub-chain, or a repeat (loops
back to an earlier step). The page shows runs live and takes answers to user
steps; every command works without it.

Read and change chains, tools, prompts and settings only with the swarm
command: "swarm list" and "swarm get PATH" to read, "swarm put" to save,
which validates and refuses with reasons. Never open, read, search or write
files under .swarm/ or ~/.swarm/ yourself, not even to look. Never run
"swarm serve" or "swarm stop"; the page belongs to the person.


FILES

~/.swarm/ is shared across projects; <project>/.swarm/ overrides it by name.

    chains/<chain>.json           a chain
    chains/<chain>/<prompt>.md    its prompts; a prompt belongs to one chain
    tools/<tool>.json             a tool
    settings.json                 agents and input defaults
    memory.md                     project only

"swarm samples" writes the samples and this guide into ~/.swarm.


COMMANDS

All act on the current folder's project; -project DIR picks another.

    swarm list                    chains to start from, then sub-chains and
                                  who uses them (with steps), tools,
                                  prompts, layers
    swarm get PATH [-below]       print one; -below: the shared one it overrides
    swarm put PATH [-file F] [-scope project|shared]
                                  validate and save F or stdin, then warn about
                                  the chains it affects; default: where it
                                  lives, else the project; shared only when
                                  the person asks
    swarm rm PATH                 delete, then warn; refused while a chain
                                  uses it
    swarm check                   validate and warn about every chain at once
    swarm settings                configured and installed agents
    swarm init [DIR]              make a folder a project
    swarm snapshot DIR            copy .swarm into DIR
    swarm diff DIR [FILE]         .swarm changes since that copy
    swarm restore DIR             put that copy back
    swarm memory                  print memory.md
    swarm memory add [-about TEXT] NOTE...
    swarm memory set [-file F]
    swarm run CHAIN [-input name=value]... [-detach]
    swarm test CHAIN [-input name=value]... [-mock JSON|FILE] [-run ID,...]
                                  dry run; see TESTING
    swarm runs [-json]            recent runs: status, duration, cost
    swarm show RUN [-json]        a run's steps with path, start, duration,
                                  cost
    swarm show RUN -step PATH [-json]
                                  one step in full: times, cost, error,
                                  every field, questions, earlier attempts,
                                  its logs
    swarm log RUN -step PATH [-json]
                                  the step's call: command, exit, stdin,
                                  stdout, stderr, result, tool calls with
                                  timing; -json has each tool call's input
                                  and output
    swarm log RUN -step PATH -stream
                                  an agent step's transcript
    swarm files RUN [PATH]        the run folder's files and the files
                                  steps show, or print one
    swarm COMMAND -h              that command's usage
    swarm cancel RUN              stop a run; "always" steps still run
    swarm approve RUN [-note T]   answer the user step a run waits on, only
    swarm revise RUN -note T      when the person tells you to
    swarm reject RUN [-note T]
    swarm answer RUN -a TEXT...   answer an agent's questions, one -a per
    swarm answer RUN -decide      question in order, or let it decide; only
                                  when the person tells you to
                                  these four take -step PATH (from swarm
                                  show, e.g. build.2.plan) when several
                                  steps are waiting

A run has its own process; "swarm run" only follows it, so your command
timing out leaves the run going. For long chains use -detach and poll
"swarm show RUN". At a user step, "swarm run" prints the question and waits.


CHAIN: chains/<chain>.json

    {
      "title": "Lint and report",
      "description": "Runs the linter and writes a short report.",
      "subject": "Lint {{target}}",
      "inputs": [
        { "name": "target", "label": "Folder to lint", "default": "." },
        { "name": "note", "label": "Anything to watch for", "optional": true }
      ],
      "vars": [{ "name": "report", "value": "{{run_folder}}/report.md" }],
      "steps": [
        { "id": "lint", "title": "Run the linter", "tool": "run_linter",
          "with": { "path": "{{target}}" } },
        { "id": "explain", "title": "Explain the findings",
          "agent": "explain-lint", "tools": ["Read", "Grep", "Glob", "Write"],
          "stop_if": "severity == none", "stop": "Nothing to fix. {{summary}}" },
        { "id": "approve", "title": "Your approval to open an issue",
          "user": "Open an issue with this report?", "show": ["{{report}}"] }
      ]
    }

title, description: shown on the page. subject: the run's heading, once
its placeholders fill; link: makes it a link. inputs: asked at start.
vars: computed at start, in order, from inputs and earlier vars. explain's
fields (summary, severity) come from chains/lint-and-report/explain-lint.md.
Names and ids: lowercase letters, digits, _; ids start with a letter.


STEPS

Each step has an id, a title saying what it does, and exactly one of:

"tool": "<tool>"
    "with" fills the tool's placeholders the chain doesn't.

"agent": "<prompt>"
    Runs an agent CLI headless in the project folder with
    chains/<chain>/<prompt>.md. claude and codex can always read and write
    {{run_folder}}; no --add-dir in settings. "runner" overrides the default agent. "tools" limits a claude step (Bash, Read, Grep, Glob,
    Write, Edit, WebFetch, WebSearch): grant the minimum, reviewers get no
    Write or Edit. Codex ignores "tools" and uses the person's Codex config.
    Returns the fields in the prompt's "## Return"; without one, free text
    as {{<id>.output}}. A "summary" field shows under the step's title.
    Each step starts a new session. "resume": "<earlier agent step>"
    continues the newest session in that line, so change, review, fix stays
    one conversation and its prompt is just the follow-up. Both steps must
    use the same CLI. Keep reviewers in a new session so they stay blind.
    A prompt whose ## Return has `questions` (list) can ask the person
    before it answers: while the list is not empty the step waits, the
    person answers each question (or lets it decide), and the agent goes
    on in the same session with the answers until it returns none.
    {{<id>.answers}} holds every question and answer; give it to later
    steps that must know what the person said, such as a blind reviewer.

"user": "<question>"
    Waits for approve or reject (reject ends the run); returns decision and
    note. "show" lists files to decide on (globs, relative to the project):
    videos play, images form a filmstrip, .md renders, .diff is coloured,
    the rest is text. The question is markdown, including any field it
    fills in, so an agent writing such a field can put files in it: list
    the file in "show", then ![what it shows](path) shows an image or video
    in place and [text](path) links to it. The path only has to be the end
    of the file's path, e.g. screenshots/before-1.png; in a shown .md it is
    relative to that file. A table row puts a before and after side by
    side:
        | Before | After |
        | --- | --- |
        | ![error](shots/before-1.png) | ![fixed](shots/after-1.png) |
    Files shown in place leave the filmstrip; a link to a file not in
    "show" is marked missing. "revise": "<earlier step>" adds a third
    answer: the note sends the run back to that step and reruns everything
    from there; a claude or codex step resumes its session with the note,
    other agent steps get all notes appended to their prompt, tools read
    {{feedback}}. Use it for reviewing any plan or draft.

"chain": "<chain>"
    Runs a sub-chain that sees the caller's values; "with" fills its
    inputs, else their defaults. Its steps' fields are then readable by
    their ids. To run it per list item, make one "with" value just the
    list, e.g. {"request": "{{split.changes}}"}: items run sequentially, each
    with its own run_folder; a reject or stop ends only that item, a
    failure fails the step after all items, and only {{<id>.summary}} is
    set ("make-change ran 3 times: 2 done, 1 rejected"). Never loop in a
    tool. "parallel": true runs the items in parallel, at most 8
    concurrently ("max_parallel": N, 2 or more, overrides it); the rest
    queue and start as items finish. The step still ends once every item
    has, and several items can wait on the person concurrently.
    "keep_going": true counts a failed item ("2 done, 1 failed") without
    failing the step, so the run goes on. All three apply only to a step
    run per list item.

"repeat": "<earlier step>"
    Goes back to that step and reruns everything from there: the steps in
    between form a loop, ending at this step. Its "when" decides each time;
    false ends the loop and the run goes on. "rounds": the most times the
    loop runs (default 3). "fail": "out_of_rounds" fails the run if it still
    wants another round after the last; "fail": "ended_early" fails it if
    the loop ends before the last round; without fail the run goes on
    either way. Takes only when, rounds and fail. Loops nest or stay apart;
    "swarm check" refuses crossing loops. A revise back before a loop's
    first step restarts its rounds; a rerun keeps them. A review loop:
      { "id": "fix", "title": "Fix the findings", "agent": "fix",
        "when": "review.verdict == CHANGES" },
      { "id": "again", "title": "Review again", "repeat": "review",
        "when": "review.verdict == CHANGES", "fail": "out_of_rounds" }

Any step may add:
    "when": "name == value" (or !=)   skip unless true; a missing name is
                                      empty, so "fix.summary != " means fix
                                      returned a summary
    "stop_if": "field == value", "stop": "<message>"
                                      after the step, end the run; reads the
                                      step's own fields
    "always": true                    run even after a failure, stop or
                                      reject; for cleanup and memory.
                                      "when": "run_status == stopped" (or
                                      failed, rejected) cleans up per ending

A failed step ends the run, apart from "always" steps.


PROCESSES

Tool and agent steps cannot hang a run or leave processes behind:
- When a step ends, everything it started is stopped, including background,
  setsid, nohup and cleared-environment processes: SIGTERM, SIGKILL 3s later.
- An agent step ends at the agent's answer, even if its CLI still waits on
  something it started.
- "stall": "<duration>" fails the step after that long idle: no new event
  for agents (default 15m); no output and no CPU for tools (10m) and custom
  agents (15m). Catches sleep and foreground servers.
- "timeout": "<duration>" fails it after that long in all (default 2h).
- Durations: 90s, 30m, 1h30m; "0" disables the limit.
- "keep_until": "<later step>" (tools only) keeps what the step started,
  such as a server, until that step ends or is skipped; the run's end stops
  the rest. Redirect a kept server's output to a file.
- git fails instead of prompting for credentials.


TOOL: tools/<tool>.json

    { "title": "Run the linter",
      "run": "npx eslint {{path}} | tee {{run_folder}}/lint.txt | tail -1" }

- run is bash, in the project folder. A non-zero exit fails the step, with
  the last stderr lines as the error.
- Filled values are already shell-quoted: write {{path}}, never "{{path}}".
- A printed JSON object becomes fields ("summary" shows on the page); other
  output becomes the field "output", its last line shown.
- Tools do deterministic work (tests, videos, commits, posts); agents do
  judgement. One job per tool; decisions go in the chain's "when", so
  commit and push are separate tools.
- For one command, use the run tool: "with": {"command": "..."}. Its
  placeholders are not quoted, so use them only for names and paths; pass
  agent text, such as a commit message, to a tool as its own value.


AGENTS

    claude   claude -p; fields through a JSON schema; honours "tools"
    codex    codex exec; fields through --output-schema; the person's config
    named    claude or codex with its own args, e.g. sonnet; acts as that one
    custom   a command from settings, e.g. pi: prompt on stdin and in
             $SWARM_PROMPT_FILE; prints the fields as one JSON object (the
             last one holding every field counts); cannot resume

A claude or codex answer without its fields is asked for them once more in
the same session.

settings.json, in ~/.swarm, overridden key by key by the project's:

    {
      "agent": "codex",
      "agents": {
        "claude": { "args": ["--model", "opus"] },
        "sonnet": { "runs": "claude", "args": ["--model", "sonnet"] },
        "pi": { "command": "pi -p" }
      },
      "inputs": { "test_command": "./test.sh" }
    }

agent: the default for agent steps. args: extra CLI arguments. runs: the
CLI a named agent runs. inputs: the starting value of any chain input with
that name, over the chain's default; adapt a shared chain per project this
way instead of copying it. Save with "swarm put settings.json -file F
-scope project"; refused if a chain would name a missing agent.


PROMPT: chains/<chain>/<prompt>.md

The agent's text, placeholders filled. Write it for its chain's step; it
moves, copies and deletes with the chain. Say what the agent gets and must
not do, then how to work, and end with:

    ## Return

    - `verdict`: `APPROVE` or `CHANGES`
    - `summary`: one plain sentence a person reads first
    - `files` (list): the files you changed
    - `score` (number): from 1 to 10

One field per line. A field is text unless its description is only
backticked choices, like verdict, or its name has (list), (number), (bool)
or (A | B | C). Every step using the prompt returns these; a Return section
swarm cannot read is refused. Add `questions` (list) to let the agent ask
the person, and say in the prompt when to ask instead of guessing and to
leave it empty once it has what it needs.


PLACEHOLDERS

{{name}} takes the first of:
  1. the step's "with"; for stop and stop_if, its returned fields first
  2. the inputs and vars of this chain and of every chain calling it
  3. project, run_id, run_folder (this run's files), memory (memory.md),
     home (~/.swarm), swarm (the binary), guide (this text), catalog
     ("swarm list"), feedback (Revise notes, oldest first), run_status
     (running until the run ends, then stopped, failed or rejected; in a
     per-item chain, how that item ended)
  4. {{step_id.field}}: an earlier step's field, sub-chain steps included,
     from its latest attempt; a step skipped, or not yet run in this round
     of a loop or revise, has no fields

An unfillable lowercase name stays as written and "swarm check" warns.
Uppercase names such as {{VIDEO_URL}} are never filled, so later steps can
replace them.


MEMORY

.swarm/memory.md holds short, true, project-specific facts a run would
otherwise rediscover: test commands, layout, conventions, traps. Prompts
read {{memory}}. make-change ends with an agent proposing notes and the
remember tool saving them.


TESTING

"swarm test CHAIN" walks the chain through the real engine (when, stop_if,
repeat, revise, sub-chains, per-item runs, parallel ones sequentially) but
runs no step. It prints each step in the order it ran, with its answer,
the command a tool would run, placeholders nothing filled, and why skipped
steps were skipped; each step's filled prompt, command or question is
saved in the folder it names.
Default answers: an agent returns its ## Return fields as examples (the
first choice, "<id.field>" for text), a user step approves, a tool returns
"<id.field>" for every field the chain reads from it. -mock picks other
paths, keyed by step id:
    {"plan": {"verdict": "STOP"}, "approve": ["revise: shorter", "approve"],
     "review": [{"verdict": "CHANGES"}, {"verdict": "APPROVE"}],
     "tests": {"fail": "2 failed"}}
A list is one answer per run of that step, then the default; {"fail": ...}
fails the step; a user step takes approve, reject or "revise: note". An
agent mock with questions gets "<answer N>" answers and goes on with the
next mock in its list.
-run names steps that really run, only read-only ones such as a lint.
Test each chain you create or change, once per path through it.


CREATING OR CHANGING

1. Run "swarm list" and reuse its tools; "swarm get PATH" shows any file.
   Prompts are not shared: a new chain gets its own, even when copied.
2. Draft a file and save it with "swarm put PATH -scope project -file
   DRAFT". Invalid JSON, unknown fields, steps without exactly one kind,
   bad conditions and missing tools, prompts or chains are refused with
   reasons. A saved put, and an rm, prints warnings for every chain it
   affects: placeholders nothing fills, fields nothing reads (summary and
   free-text output are exempt). Fix the draft and put it again until
   both are clean; no separate check is needed.
3. Put tools and prompts before the chain that uses them.
4. To change a shared item for one project, "swarm get PATH > DRAFT", edit,
   and put it with -scope project. A project copy of a chain takes its
   prompts and then reads only its own. If only a value differs, set it
   under "inputs" in the project's settings.json instead.
5. Anything leaving the machine (push, post, upload, message) goes after a
   user step that shows the files to decide on.

The edit-chain sample does this from a plain request: snapshot, an agent
edits, check, the diff for approval, restore on rejection.
